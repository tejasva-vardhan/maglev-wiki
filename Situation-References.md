# Situation References

## Purpose

This page defines the shared contract for service-alert situation IDs and `data.references.situations` across OBA `where` API responses. Endpoint pages should describe where their own `situationIds` fields appear and link here for the dereferencing rule.

## Legacy Java behavior

For most endpoints, legacy Java only adds service-alert situation beans to `data.references.situations` while it is also emitting a `situationIds` array in the response data. The shared `BeanFactoryV2.addToReferences(ServiceAlertBean)` helper deduplicates the situation reference and respects `includeReferences=false` through `shouldAddReferenceWithId(...)` ([`BeanFactoryV2.java#L1585-L1592`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L1585-L1592), [`#L1623-L1627`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L1623-L1627)). The explicit situation-ID paths are:

- `TripStatusV2Bean`: copies `TripStatusBean.getSituations()` to `status.situationIds` and adds each situation to references ([`BeanFactoryV2.java#L600-L607`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L600-L607)).
- `TripDetailsV2Bean`: copies `TripDetailsBean.getSituations()` to `entry.situationIds` and adds each situation to references ([`BeanFactoryV2.java#L679-L686`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L679-L686)).
- `StopWithArrivalsAndDeparturesV2Bean` and `StopsWithArrivalsAndDeparturesV2Bean`: copy stop-level situations to `entry.situationIds` and add each situation to references ([`BeanFactoryV2.java#L1215-L1222`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L1215-L1222), [`#L1252-L1259`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L1252-L1259)).
- `ArrivalAndDepartureV2Bean`: copies per-arrival situations to `situationIds` and adds each situation to references ([`BeanFactoryV2.java#L1339-L1346`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L1339-L1346)).

Legacy Java has one known ambient exception: `schedule-for-route`. The route-schedule service queries route/stop service alerts and stores them on `RouteScheduleBean` ([`RouteScheduleBeanServiceImpl.java#L117-L135`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-transit-data-federation/src/main/java/org/onebusaway/transit_data_federation/impl/beans/RouteScheduleBeanServiceImpl.java#L117-L135), [`RouteScheduleBean.java#L116-L120`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-transit-data/src/main/java/org/onebusaway/transit_data/model/RouteScheduleBean.java#L116-L120)). `addSituations` does not set a query time; `SituationQueryBean` defaults `time` to `-1`, and the alert service skips publication-window filtering when `time == -1` ([`SituationQueryBean.java#L44-L53`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-transit-data/src/main/java/org/onebusaway/transit_data/model/service_alerts/SituationQueryBean.java#L44-L53), [`ServiceAlertsServiceImpl.java#L457-L464`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-alerts-persistence/src/main/java/org/onebusaway/alerts/impl/ServiceAlertsServiceImpl.java#L457-L464)). The response factory then writes those alerts directly into `references.situations` ([`BeanFactoryV2.java#L996-L999`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/BeanFactoryV2.java#L996-L999)), even though `RouteScheduleV2Bean` has no `situationIds` field ([`RouteScheduleV2Bean.java#L51-L54`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-core/src/main/java/org/onebusaway/api/model/transit/RouteScheduleV2Bean.java#L51-L54)). See [[schedule-for-route]] for Maglev's intentional deviation from this legacy exception.

## Maglev implementation contract

Maglev uses a simpler invariant for all OBA `where` responses:

> `data.references.situations` contains exactly the service-alert situation objects needed to resolve `situationIds` values that appear somewhere in the response data. If the response data has no `situationIds` values, `data.references.situations` is empty.

Consequences:

- A situation reference must not appear ambiently just because the queried agency, route, stop, or trip has an active alert.
- Every non-empty `situationIds` array value should have a matching object with the same `id` in `data.references.situations`, unless references are suppressed by `includeReferences=false`.
- Endpoints without `situationIds` fields return an empty `data.references.situations` array, even if service alerts exist for the queried entities.
- `schedule-for-route` intentionally diverges from legacy Java by not preserving its ambient route/stop situation references; see [schedule-for-route § Implementation Decisions](schedule-for-route.md#implementation-decisions).
- `search-stop` follows the same invariant: because the legacy and intended response shape has no `situationIds` field, `data.references.situations` remains empty. If a future response shape adds explicit `situationIds`, this page's normal dereferencing rule applies.

This rule does not apply to `/api/where/situation/{id}` when the situation itself is the primary `data.entry`; the primary entry is not a reference-block member.

## Situation ID formation

Legacy Java prefixes GTFS-RT alert IDs unconditionally with the first agency configured on the GTFS-RT feed: `GtfsRealtimeSource.handleAlerts` calls `createId(entity.getId())`, and `createId` returns `new AgencyAndId(_agencyIds.get(0), id)` ([`GtfsRealtimeSource.java#L1064-L1065`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-transit-data-federation/src/main/java/org/onebusaway/transit_data_federation/impl/realtime/gtfs_realtime/GtfsRealtimeSource.java#L1064-L1065), [`#L1176-L1177`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-transit-data-federation/src/main/java/org/onebusaway/transit_data_federation/impl/realtime/gtfs_realtime/GtfsRealtimeSource.java#L1176-L1177)). Maglev intentionally uses idempotent agency prefixing (`situationID()` in `internal/restapi/reference_utils.go`) and prefers an agency ID from the alert's own informed entities (`agencyIDForAlert()`) when one is present. Endpoint pages that expose `situationIds` may link here rather than repeating that Maglev-wide implementation decision.

Rationale: some GTFS-RT feeds already publish alert IDs in `{agencyId}_{alertId}` form, and unconditional Java-style prefixing would double-prefix those alerts. In multi-agency real-time feeds, deriving the prefix from the alert's own informed entity also avoids publishing the same alert under different IDs depending on which lookup path found it first.

Fallback if reconsidered: restore Java's unconditional feed-first-agency prefixing, accepting the double-prefix regression for feeds that already publish prefixed alert IDs and the two-IDs-for-one-alert risk for cross-agency lookups.
